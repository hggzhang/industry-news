# AI Weekly Intelligence Skill

## 1. 目标与定位

本 Skill 用于生成高信噪比的 **AI
周度情报与行业分析报告**，不是七份日报的拼接，也不是普通新闻周报。

周报的核心任务：

1.  回顾上一完整自然周 AI 行业发生的关键变化。
2.  识别真正改变技术能力、产品竞争、工具链、生产工作流、平台规则或商业格局的事件。
3.  将一周内分散的信息合并为有证据支撑的行业判断。
4.  识别短期和中期趋势，并与此前数周的信号进行对比。
5.  判断哪些工具、技术和工作流值得用户尝试、学习或持续跟踪。
6.  将本周信息转化为少量具体的下周行动建议。

周报必须与具体模型和平台解耦。任何支持联网搜索、网页阅读和基本推理的
Agent / 大模型都应能够执行。

## 2. 与 AI 日报的职责边界

日报和周报是两个独立 Skill，职责不同：

  ------------------------------------------------------------------------------------------
  维度                    日报                    周报
  ----------------------- ----------------------- ------------------------------------------
  目的                    及时发现重大变化        理解一周的行业变化

  时间窗口                最近完整 24 小时为主    上一完整自然周

  信息等级                仅重大                  重大、重要、一般

  分析方式                单事件判断              事件整合、趋势与跨周比较

  输出重点                发生了什么、为何重大    发生了什么、变化意味着什么、下一步做什么

  触发                    手动                    手动
  ------------------------------------------------------------------------------------------

周报可以引用本周日报已经报道的事件，但不得简单复制。必须加入新的汇总、比较、背景、影响或判断。日报中的重大事件在周报中可以成为证据，但不能仅靠重复日报内容充当周报分析。

## 3. 用户目标优先级

用户获取 AI 信息的主要目的，按优先级排序：

1.  工作提效与 AI 应用落地
2.  学习 / 科研
3.  职业发展
4.  跟上行业变化
5.  兴趣了解
6.  投资 / 商业判断

周报优先回答：本周哪些变化会影响实际工作、生产流程、工具链、技能结构和技术判断？哪些变化值得投入时间？哪些只是短期噪声？

## 4. 用户行业与高相关领域

重点关注：

-   AIGC
-   AR / VR / XR / 空间计算
-   游戏
-   3D / 建模
-   影视
-   AI 编程

这些领域的工作流、工具、平台、硬件、标准和商业变化应获得较高相关性权重。但不得因为领域偏好而漏掉真正具有行业级影响的其他
AI 事件。

## 5. 信息主题优先级

总体优先级：

1.  AI 编程与开发工具
2.  AI 产品与应用
3.  开源模型与开源项目
4.  科研论文与技术进展
5.  大模型与基础模型
6.  Agent / 智能体
7.  芯片、算力与基础设施
8.  AI 公司、融资与商业动态
9.  政策、监管与安全

### 5.1 AI 编程与开发工具内部优先级

1.  已有工具的重要更新
2.  新工具 / 新产品发布
3.  实际使用效果、真实项目体验、Benchmark
4.  开发方法与工作流
5.  API / SDK / 框架 / 基础设施更新

### 5.2 AI 产品与应用内部优先级

1.  自动化与 Agent 类产品
2.  搜索、知识管理、研究辅助类产品
3.  图像、视频、音频生成类产品
4.  面向普通用户的 AI 产品
5.  面向企业 / 办公场景的 AI 产品

### 5.3 开源模型与开源项目内部优先级

1.  开源 Coding / Agent 项目
2.  GitHub 上快速增长、可能形成生态的新项目
3.  新开源大模型
4.  模型性能对比、榜单与 Benchmark
5.  推理 / 训练 / 部署框架
6.  开源多模态模型

### 5.4 科研论文与技术进展

综合技术突破性、来源质量、工程落地价值，以及与 AI
编程、Agent、大模型的相关性。不得只以是否顶会 / 顶刊作为唯一标准。

## 6. 重点额外关注项

周报必须主动搜索会改变生产方式、工具链或行业结构的变化。

### 6.1 创作工作流变化

-   AI 视频进入影视生产流程
-   3D 生成进入建模流程
-   AI NPC / Agent 进入游戏开发
-   XR 内容生产工具链变化
-   AI 编程改变研发流程
-   动作捕捉、角色动画、数字人、材质、资产生成等流程变化

### 6.2 可直接用于生产的工具与能力

-   文生图 / 文生视频
-   视频编辑 / 镜头控制
-   3D 生成 / 资产生成
-   角色动画 / 动作捕捉
-   材质生成、数字人、游戏资产生成
-   AI 编程助手 / Coding Agent
-   可嵌入生产流程的 API、插件、工作站和设备

### 6.3 行业应用案例

重点关注 AIGC、游戏开发、XR / 空间计算、影视制作、3D 建模和 AI
编程。案例规模可以较小，但必须有明确启发性和可验证细节。

### 6.4 硬件与设备端 AI

关注 GPU / NPU、AI PC、XR 头显、空间计算设备、端侧模型、实时渲染与 AI
加速等会影响生产的变化。

### 6.5 内容平台与分发端变化

关注 YouTube、TikTok、Bilibili、抖音、Steam、App Store、Meta Horizon
等平台的 AI 内容标注、推荐机制、商业化、版权和上架 / 分发规则变化。

### 6.6 标准、协议与生态兼容性

只关注已被头部厂商广泛采用或明显进入主流生态的标准 / 协议，例如 USD /
OpenUSD、glTF、MCP、OpenXR、WebXR，以及重要模型上下文、3D、动画和资产交换标准。

### 6.7 招聘与岗位变化

仅当岗位变化明显反映行业趋势时收录，例如新岗位类型快速增加、技能要求成为主流、岗位被重构或头部公司招聘方向体现战略转向。

### 6.8 资本与公司经营

只关注重大融资、并购、明显战略变化、业务收缩 / 扩张，以及可能改变 AI
行业格局的经营变化。

## 7. 时间窗口与补漏规则

### 7.1 默认时间窗口

-   主窗口：上一完整自然周，周一 00:00 至周日 23:59:59。
-   例如：在周三手动生成时，默认复盘刚刚结束的周一至周日，而不是滚动过去
    7 天。
-   用户明确指定日期范围时，以用户指定范围为准。
-   报告标题和开头必须写清统计起止日期及所用时区。

### 7.2 时区规则

优先使用用户明确指定的时区；未指定时，使用执行环境能够可靠确认的用户本地时区。若无法确定且会影响周一
/ 周日边界，应先询问用户，不得默认为中国时区或 UTC。

### 7.3 历史补漏窗口

允许补充过去 30 天内此前遗漏、但仍然重要的信息，必须同时满足：

-   此前未在周报中充分覆盖，或此前缺少关键事实；
-   当前仍具有明显行业、技术、工作流、学习或商业价值；
-   能说明为什么本周仍值得重新纳入；
-   标明原始发布时间 / 事件发生时间；
-   不得伪装成本周新发生的事件。

更早的信息原则上不纳入，除非它是理解本周重大变化所必需的背景。背景必须标注原始时间，不得占据周报主体。

### 7.4 手动触发

本 Skill
仅在用户明确要求时运行。不自动生成、不定时推送、不后台持续搜索、不创建自动任务。

可识别的触发语句：

-   "生成上周 AI 周报。"
-   "按 AI Weekly Intelligence Skill 跑一遍。"
-   "复盘上一完整自然周 AI 行业的变化。"
-   "给我一份本周 AI 行业周度情报。"

## 9. 来源可信度与事实核验

### 9.1 中文非官方内容

B站、知乎、抖音、微博等非官方内容可以作为发现线索或体验材料，但必须：

-   明确标注"社区 / 二手来源"；
-   说明是否完成交叉验证；
-   涉及重大事实时，尽量寻找官方 / 一手来源；
-   体验、评测、观点可以独立收录，但不得伪装成已确认事实。

必要时区分事实、评测、观点和预测。

### 9.2 传闻与泄露

可以进入候选池，但必须同时满足：

-   潜在影响较大；
-   来源具有一定可信度；
-   明确标注"未确认 / 爆料 / 传闻"；
-   说明来源、现有证据与争议点；
-   不得把推测写成事实。

证据不足时应剔除或放入"观察项"，不得写成已确认事件。

### 9.3 官方宣传与 Benchmark

官方发布可以收录，但性能或效果缺乏独立验证时必须注明："官方自述，尚缺独立验证。"

Benchmark
在适合时说明名称、测试设置、是否为官方自测、是否有第三方结果，以及对实际工作流的意义。不得把单一
Benchmark 当成全面能力证明。

### 9.4 重大事实交叉验证

重大事件优先寻找官方 /
一手来源，并在必要时用可靠媒体、论文、仓库或独立实测交叉验证。只有单一来源时，明确说明证据局限。

## 10. 去重、事件合并与低价值剔除

### 10.1 周内跨日去重

-   同一事件在一周内被多次报道，只保留一个主条目。
-   将不同媒体、不同日期的报道合并为同一事件的证据链。
-   同一事件若在一周内出现多个实质阶段，可以在一个条目内按时间线说明，不得拆成多条重复新闻。
-   重大事件可保留多个来源，以补充不同角度和证据。

### 10.2 跨主题合并

多个事件若共同指向同一技术方向、产品趋势或工作流变化，应在趋势分析中综合讨论；但每个事件的事实边界必须清晰，不能把不同公司的能力混为一谈。

### 10.3 历史报道去重

补漏信息必须与本周新进展区分。若同一事件此前已报道且本周没有新增事实，不重复列为本周事件；确有必要时只作为趋势背景引用。

### 10.4 低价值信息剔除

主动剔除：

-   与重点领域关系弱且行业影响小
-   重复报道、旧闻再包装
-   标题党、纯营销稿、没有实际变化的宣传
-   纯概念炒作
-   没有新增产品、技术、政策、商业或工作流变化
-   仅因热度高但没有实质进展
-   普通促销、小幅调价和常规版本维护
-   无法验证且影响判断所需证据不足的传闻

周报不设置固定条数上限，但必须主动裁掉低价值内容，不得凑数。

## 11. 信息重要性分级与评分机制

周报采用三级：

-   重大
-   重要
-   一般

对候选信息从七个维度评分，每项 0--5 分。

### 11.1 行业影响范围 I

-   0：几乎无影响
-   1：小众产品 / 单一用户群
-   2：单一细分领域
-   3：多个细分领域
-   4：大范围 AI 产业 / 开发者生态
-   5：可能改变行业格局或基础能力边界

### 11.2 用户相关性 R

根据 AIGC、AR/VR/XR、游戏、3D 建模、影视、AI 编程等领域评估：

-   0：基本无关
-   1：弱相关
-   2：间接相关
-   3：有明确参考价值
-   4：可影响当前工具 / 工作流
-   5：直接影响生产方式、工具选择或核心技能

### 11.3 技术突破程度 T

-   0：无技术变化
-   1：小改动
-   2：常规迭代
-   3：明显能力提升
-   4：重要技术跃迁
-   5：明显改变当前技术边界

### 11.4 落地与可用性 P

-   0：纯概念
-   1：研究原型
-   2：有限可用
-   3：已有实际使用路径
-   4：可直接进入生产 / 工作流
-   5：显著降低成本或重构生产流程

### 11.5 新颖性 N

-   0：完全重复
-   1：旧闻再包装
-   2：小补充
-   3：有新事实
-   4：明显新能力 / 新产品 / 新政策
-   5：首次出现的重要变化

周报评估新颖性时，以本周新增事实和相对前几周的增量为准，不因旧事件本身仍然重要而虚增新颖性。

### 11.6 可信度 C

-   0：匿名无证据
-   1：低可信二手来源
-   2：有一定依据但未验证
-   3：可靠媒体 / 开发者实测
-   4：官方 / 一手来源
-   5：官方 + 第三方 / 多来源交叉验证

### 11.7 持续影响力 L

-   0：当天即过时
-   1：短暂热点
-   2：持续数天
-   3：可能持续数周 / 数月
-   4：可能影响一个阶段
-   5：可能长期改变生态或工作方式

### 11.8 总分

`Total = 0.20×I + 0.20×R + 0.15×T + 0.15×P + 0.10×N + 0.10×C + 0.10×L`

总分范围为 0--5。

### 11.9 等级映射

**重大：**

-   Total ≥ 4.1；或
-   Total ≥ 3.7，且 I ≥ 4，且 T / P / L 中至少两项 ≥ 4；或
-   属于明显改变基础模型、主流工作流、平台规则、产业格局或安全边界的事件。

**重要：**

-   Total ≥ 3.1；或
-   对用户当前行业 / 工作流直接相关，R ≥ 4 且 P ≥ 3；或
-   影响范围有限，但具有明显生产、学习或职业价值。

**一般：**

-   未达到重大 / 重要，但仍具有明确信息价值。
-   一般信息不得因为数量需要而强行保留。

事实可信度是独立约束，不能仅凭高影响潜力把证据不足的传闻判为已确认重大事件。

### 11.10 强制保留

即使用户短期用不上，只要满足以下之一，仍应正常收录：

-   行业级重大事件
-   可能改变主流技术路线
-   重要模型 / 平台 / 硬件基础能力变化
-   重要政策 / 安全 / 版权变化
-   重大并购或产业战略变化

## 12. 周报专属综合分析

本节是周报相对日报最重要的增量。不得只罗列事件，必须在证据允许时完成以下分析。

### 12.1 一周事件脉络

对一周内相互关联的事件进行时间线梳理，说明：

-   本周出现了什么新事实；
-   与此前进展相比新增了什么；
-   事件之间是否存在因果关系，还是仅仅时间接近；
-   哪些变化已经落地，哪些仍停留在发布、测试或传闻阶段。

不得为了叙事完整而虚构因果关系。

### 12.2 本周核心结论

提炼少量最重要的结论，覆盖：

-   本周最重要的技术 / 产品 / 行业变化；
-   对用户重点领域最有影响的变化；
-   最值得尝试或学习的机会；
-   最需要警惕的风险或不确定性。

核心结论必须能追溯到后文具体事件和来源，不得写成空泛口号。

### 12.3 本周行业变化总结

独立分析本周已经发生的结构性变化，重点检查：

-   技术能力边界是否改变；
-   产品竞争格局是否改变；
-   工具链和主流工作流是否改变；
-   某些技术是否从实验阶段进入生产阶段；
-   商业模式、成本结构或平台规则是否改变；
-   岗位需求、技能要求或职业分工是否改变。

只写有证据支持的实际变化。没有明显结构性变化时，明确说明，不强行生成结论。

### 12.4 趋势分析

从多条事件中识别共同信号，并判断：

-   趋势描述；
-   支持该趋势的独立信号和来源；
-   与前几周相比是加速、减速、延续还是反转；
-   影响哪些领域和工作流；
-   短期（未来几周至几个月）可能如何发展；
-   中期（未来半年至两年）可能产生什么影响；
-   置信度与反面证据。

趋势必须由多个可靠信号支撑。原则上至少有两个相互独立的信号；若来源相互转载或都来自同一家公司，不视为独立证据。单条新闻只能作为观察信号，不得升级为行业趋势。

### 12.5 跨周比较

在有可靠历史材料时，与前几周的变化进行比较：

-   新出现的能力或产品；
-   已有趋势是否持续；
-   重要方向是否加速或降温；
-   竞争者之间的差距是否变化；
-   行业关注点是否转移；
-   上周判断是否得到验证、被修正或被推翻。

不得假装拥有未实际检索到的历史周报。缺少历史资料时，明确说明比较范围受限，并用可查证的历史公开信息作为背景。

### 12.6 工具与工作流评估

筛选真正值得尝试的工具、技术或工作流，说明：

-   解决什么问题；
-   当前可用程度；
-   适合什么场景；
-   与现有方案相比的优势和限制；
-   成本、集成、版权、隐私和迁移风险；
-   建议先做什么小规模验证。

不要把所有新品都列入"值得尝试"。

### 12.7 重大事件持续追踪

只追踪重大事件。后续出现以下实质变化时更新：

-   实际测试结果
-   API / 产品正式开放
-   价格重大变化
-   开源复现
-   安全问题
-   行业采用
-   重大社区反馈
-   商业 / 政策后果

没有新增事实或实质进展时不重复报道。更新时关联此前进展，突出本周增量。

### 12.8 下周值得关注的事项

仅列出下周有明确依据的事项，例如：

-   已公布的产品发布、开发者大会或政策生效日期；
-   已确认的测试、开放、交付或版本计划；
-   可能影响行业判断的明确时间节点。

每项需标注日期、事件、来源，以及"已确认 / 预计 /
未确认"状态。没有可靠依据的猜测不得伪装成日程。若无明确事项，可省略该模块。

### 12.9 下周行动计划

从本周信息中提炼少量、具体、可执行的行动：

-   优先级：高 / 中 / 低；
-   行动：做什么；
-   目的：希望验证或获得什么；
-   场景：适用于什么工作或项目；
-   完成标准：怎样判断行动有结果。

只在确有行动价值时输出，不为凑数生成任务。行动应优先考虑工作提效、学习价值和真实项目验证。

## 13. 排序规则

### 13.1 事件排序

本周重要事件按重大、重要、一般三级分层。每个等级内部按综合重要性排序，不按主题分组，也不按发布时间简单排序。

### 13.2 同级排序参考

综合考虑行业影响、用户相关性、新颖性、实用性、技术突破程度、持续影响和证据质量。

### 13.3 分析模块与事件列表去重

趋势分析、行业变化总结和核心结论可以引用事件编号或标题，但应聚焦综合判断，不要再次完整复述事件正文。

## 14. 每条事件的输出要求

根据事件类型动态组织，不机械填满字段。通常包含：

1.  标题
2.  类型标签
3.  重要等级
4.  发生了什么
5.  为什么重要
6.  关键技术 / 产品 / 商业细节
7.  对用户可能的影响
8.  行动建议
9.  风险提示（存在明显风险时）
10. 机会提示（存在明显机会时）
11. 学习提示（值得学习时）
12. 趋势信号（若与更大趋势相关）
13. 横向对比（有明确可比对象时）
14. 来源链接
15. 必要时说明发布时间、事件时间、可信度、是否独立验证

"发生了什么 + 为什么重要 +
来源"应尽量保留。重大事件需要深入分析；重要事件采用中等深度；一般事件简洁概述。不要为了统一格式而牺牲可读性。

### 14.1 类型标签

可使用一个或多个：

AI 编程、产品、Agent、开源、大模型、科研、AIGC、视频、图像、3D /
建模、游戏、XR / 空间计算、影视、硬件、平台、标准 / 协议、商业、政策 /
监管、安全、招聘 / 岗位趋势、社区趋势。

### 14.2 行动建议

建议说明做什么、为什么、适合在哪个场景尝试。不得用"建议关注"代替具体建议。

### 14.3 横向对比

存在明确可比对象时，动态选择能力效果、价格与成本、速度、工作流集成、商用许可、版权风险、易用性和生态成熟度等维度。不得为了对比而对比。

### 14.4 风险提示

必要时指出版权 / 商用许可、数据隐私、模型输出合规、API
稳定性、供应商锁定、价格变化、宣传与实际效果不一致、未经验证的
Benchmark、生态成熟度、工作流迁移成本和平台政策风险。

### 14.5 机会与学习提示

存在明显机会时指出产品、内容生产、游戏玩法、XR 交互、建模、影视、AI
编程、岗位技能或商业化机会。值得学习时给出知识点、官方文档 / 论文 /
项目和一个可做的小实验；不要展开成完整课程。

## 15. 社区热度、价格与外部信号

### 15.1 社区热度与开发者舆情

关注 GitHub Star 快速增长、开发者迁移、Hacker News / Reddit / X / 知乎 /
B站持续讨论、工具生态形成和真实用户反馈。社区热度可作为趋势证据，但不能替代事实验证。

### 15.2 价格变化

只有在明显影响工具选择、使用成本、API
成本、生产工作流或规模化部署时才进入周报。普通促销、小幅调价不收录。

### 15.3 招聘与岗位趋势

只有多个招聘信号或头部公司明确动作足以反映岗位结构、技能要求或战略变化时，才作为行业变化分析。

## 16. 长期追踪清单与用户偏好

-   只有用户明确要求加入时，才真正加入长期追踪清单。
-   Agent 可以主动建议加入某个主题，但必须由用户确认。
-   不得因用户点开或追问某条内容就自动改变长期偏好。
-   只有用户明确说"多关注 / 少关注 / 加入追踪 / 取消追踪"时才调整偏好。

## 17. 输出形式与推荐模板

默认先在 AI 对话中完整输出。结尾询问是否生成 Markdown
文档，不自动创建文件。

推荐模板：

# AI 周报｜YYYY-MM-DD 至 YYYY-MM-DD

**统计周期：** 周一 00:00 至周日 23:59:59（注明时区）\
**补漏范围：** 如有，注明过去 30 天内补充的信息及其原始日期。

## 一、本周核心结论

用少量要点概括本周最重要的行业变化、技术进展、用户相关影响和关键判断。每个结论应能追溯到后文事件。

## 二、本周重要事件

### 1. \[重大\] \[类型标签\] 标题

-   **发生了什么：**
-   **为什么重要：**
-   **关键细节：**
-   **对你的影响：**
-   **行动建议：**
-   **风险 / 机会 / 学习提示：** 按需提供。
-   **横向对比：** 有明确可比对象时提供。
-   **来源：**

按重要性继续列出重大、重要、一般事件。各级内部统一按重要性排序，不按主题机械分组。一般事件只有确有信息价值时才保留。

## 三、本周行业变化总结

从技术能力、产品竞争、工作流、商业模式、平台规则和岗位技能等角度总结实际发生的结构性变化。没有明显变化时说明证据不足，不强行总结。

## 四、本周趋势分析

每个趋势至少说明：

-   趋势判断
-   支持信号与来源
-   相较前几周的变化
-   影响领域
-   短期 / 中期判断
-   置信度与反面证据

没有足够证据的方向放入观察项，不称为趋势。

## 五、值得尝试的工具与工作流

只列出本周真正值得测试的工具、技术或生产流程，说明用途、适用场景、限制和建议验证方法。

## 六、重大事件追踪

只列出本周出现实质进展的重大事件，简要说明此前进展、本周新增内容和后续影响。无更新时可省略。

## 七、下周值得关注的事项

列出有来源的已公布日程或明确时间节点，标注日期与确认状态。无可靠事项时可省略。

## 八、下周行动计划

只列少量有明确价值的行动，按高 / 中 /
低优先级排列，并给出目的、场景和完成标准。没有必要行动时可省略。

### 17.1 结尾交互

每次正常生成周报后，最后询问：

"是否需要我把这份 AI 周报整理成 Markdown 文档？"

## 18. 链接与来源要求

每条事件都应提供可访问的来源链接，优先级：

1.  官方 / 一手来源
2.  原论文 / 原仓库
3.  可靠主流媒体
4.  高质量社区实测 / 讨论

重大事件可以提供多个来源。趋势判断应提供支撑该判断的多个来源。不得堆砌重复链接；链接必须支持对应事实。

## 19. 技术深度

默认技术深度为适中：

-   重大事件：深入说明关键原理、指标、技术变化、限制和落地影响。
-   重要事件：说明核心变化、实际价值和主要限制。
-   一般事件：简洁说明新增事实和保留理由。

无需展开公式或过度学术化。重大技术突破可以适当增加解释，但应保持周报可读性。

## 20. 不得做的事情

-   不得把七份日报简单拼接成周报。
-   不得把旧闻包装成本周新事件。
-   不得为了固定条数而凑新闻。
-   不得只搜英文来源或只搜中文来源。
-   不得只看媒体而忽略官方来源。
-   不得把社区观点写成事实。
-   不得把公司宣传写成独立验证结果。
-   不得把单一 Benchmark 当成全面能力证明。
-   不得把热门话题自动视为重要。
-   不得因用户行业偏好而漏掉行业级重大事件。
-   不得用空泛的"值得关注"代替具体分析。
-   不得把单条新闻夸大成行业趋势。
-   不得把相关性误写成因果关系。
-   不得重复报道没有实质进展的重大事件。
-   不得假装拥有未检索到的历史周报或历史数据。
-   不得自动修改用户长期偏好。
-   不得自动运行、定时推送或后台持续搜索。
-   不得绑定某一个特定模型或平台。

## 21. 运行流程

每次手动触发时：

1.  确认上一完整自然周的起止日期与时区；若用户指定自定义周期则遵循指定范围。
2.  建立过去 30 天补漏候选池，识别此前遗漏且仍重要的信息。
3.  搜索核心来源类别，同时覆盖全球和中国。
4.  主动搜索中文平台、中国 AI 公司和海外社区。
5.  根据本周热点扩展搜索新来源、新公司和新项目。
6.  建立候选事件池，记录事件日期、首次发布时间和本周新增事实。
7.  对跨日、跨媒体、跨主题报道去重和合并。
8.  对重大事实进行必要交叉验证。
9.  标记传闻、社区信息、官方自述和 Benchmark 验证状态。
10. 按七维评分机制评估候选事件。
11. 分为重大、重要、一般，剔除低价值信息。
12. 检查重大事件是否有跨周实质进展。
13. 将关联事件整合为事件脉络，避免重复罗列。
14. 形成本周核心结论和行业变化总结。
15. 只有在多个可靠信号支持时才形成趋势判断，并尽可能与前几周比较。
16. 筛选值得尝试的工具与工作流。
17. 搜索并核实下周已公布的重要事项。
18. 从本周信息中提炼少量可执行的下周行动。
19. 检查是否遗漏 AIGC / XR / 游戏 / 建模 / 影视 / AI
    编程相关工作流变化。
20. 检查中国来源、全球来源和每条信息的来源链接。
21. 检查历史补漏是否标明原始时间，是否误写为本周新事件。
22. 按模板在对话中输出周报。
23. 询问是否生成 Markdown 文档。

## 22. 质量检查清单

输出前必须自检：

-   是否使用上一完整自然周，而非误用滚动 7 天？
-   是否写清起止日期和时区？
-   是否仅在用户手动触发后运行？
-   是否同时覆盖全球和中国信息？
-   是否主动搜索中文平台和中国 AI 公司？
-   是否覆盖 AI 编程、AIGC、XR、游戏、建模、影视的变化？
-   是否优先发现工作流变化？
-   是否将同一事件跨日、跨媒体去重？
-   是否合并关联信息，同时保留事实边界？
-   是否区分本周新事件与历史补漏？
-   是否对重大事实进行必要核验？
-   是否把未经验证的信息明确标记？
-   是否对官方自述注明缺乏独立验证（如适用）？
-   是否每条事件都有可靠来源？
-   是否按评分机制分为重大、重要、一般？
-   是否没有为了凑数保留低价值信息？
-   是否形成有证据支撑的本周核心结论？
-   是否区分实际行业变化与未来趋势判断？
-   每个趋势是否有多个独立信号支持？
-   是否避免把相关性写成因果关系？
-   是否在资料允许时与前几周比较，且没有编造历史信息？
-   是否指出值得尝试的工具和工作流，而非罗列新品？
-   是否只追踪有实质进展的重大事件？
-   下周事项是否有来源并标注确认状态？
-   下周行动是否具体、少量且可执行？
-   是否避免在多个模块重复复述同一事件？
-   是否保持手动触发，没有创建自动任务？
-   是否在结尾询问是否生成 Markdown 文档？

## 23. 默认行为总结

这是一个"全球 + 中国双覆盖、以上一完整自然周为主、允许 30
天内必要补漏、先广搜后筛选、按重要性分级、合并跨日重复事件、识别行业变化与趋势、对重大事件持续追踪、强调生产工作流和实际可用性、形成下周行动计划"的
AI 周度情报系统。

周报的目标不是让用户看到更多新闻，而是帮助用户理解一周内真正发生了什么变化、这些变化意味着什么，以及下一步应该关注、学习和尝试什么。
